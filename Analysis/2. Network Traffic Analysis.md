## Application Layer

The **application header** and the **application itself (payload)** are making the application layer. 


For example, you can see the traffic itself, but not the exact files:
	In case you'd download a suspicious package, you'd see it in the network logs:
```json
GET /downloads/suspicious_package.zip HTTP/1.1
Host: www.tryhackrne.thn
User-Agent: curl/7.85.0
Accept: */*
Connection: close
```

However, you wouldn't see the suspicious_package.zip's contents, only the HTTP response


## Transport Layer


The application data and header are **segmented and encapsulated at the transport layer**, into smaller pieces.

Each piece includes a **TRANSPORT HEADER**, which are **TCP** and **UDP**!

```json

2025-10-13 09:15:32 ACCEPT TCP src=192.168.1.45 dst=172.217.22.14 sport=51432 dport=443 flags=SYN len=60
2025-10-13 09:15:32 ACCEPT TCP src=172.217.22.14 dst=192.168.1.45 sport=443 dport=51432 flags=SYN,ACK len=60

```
They are useful for detecting `Session Hijacking` for instance, which can be detected by _analyzing the sequence numbers_ from the header!

```json
No.     Time        Source          Destination     Protocol Length  Info
1       0.000000    192.168.1.45    172.217.22.14   TCP      74      51432 → 80 [SYN] Seq=0 Win=64240 Len=0 MSS=1460
2       0.000120    172.217.22.14   192.168.1.45    TCP      74      80 → 51432 [SYN, ACK] Seq=0 Ack=1 Win=65535 Len=0 MSS=1460
3       0.000220    192.168.1.45    172.217.22.14   TCP      66      51432 → 80 [ACK] Seq=1 Ack=1 Win=64240 Len=0
4       0.010500    192.168.1.45    172.217.22.14   TCP      1514    51432 → 80 [PSH, ACK] Seq=1 Ack=1 Win=64240 Len=1460
5       0.010620    172.217.22.14   192.168.1.45    TCP      66      80 → 51432 [ACK] Seq=1 Ack=1461 Win=65535 Len=0
6       0.020100    192.168.99.200  172.217.22.14   TCP      74      51432 → 80 [PSH, ACK] Seq=34567232 Ack=1 Win=64240 Len=20  
```
Here you can see at _the 6th Seq's value is 34567232_, which is quite unusual.

Here is a breakdown:
- The first 3 lines show a normal TCP 3-way handshake
- Lines 4-5 show legitimate data transfer
- Line 6 shows a packet from another source, trying to inject itself into the session, which also comes with a large sequence number!


## Internet Layer

When the transport layer sends down a segment, the internet layer also adds its header. If the segment is larger than the Maxim Transmission Unit (**MTU**), it will be divided into fragments.


**Logged**:
	Source-, destination IP and TTL 

**Not Logged**:
	fragment offset and total length.

**Attack**:
	Fragmentation attack is done e.g by an attacker _creating tiny fragments to evade the IDS_ by overlapping byte ranges. For example:

```json
No.   Time       Source        Destination   Protocol Length Info
1     0.000000   203.0.113.45  192.168.1.10  UDP      1514    Fragmented IP protocol (UDP) (id=0x1a2b) [MF] Offset=0, Len=1480
2     0.000015   203.0.113.45  192.168.1.10  UDP      1514    Fragmented IP protocol (UDP) (id=0x1a2b) [MF] Offset=1480, Len=1480
3     0.000030   203.0.113.45  192.168.1.10  UDP       600    Fragmented IP protocol (UDP) (id=0x1a2b) Offset=1480, Len=64   <-- Overlap
4     0.000045   192.168.1.10  203.0.113.45  ICMP      98     Destination unreachable (Fragment reassembly time exceeded)
```

## Link Layer

Once the internet layer finishes encapsulation, the IP packet is sent to the link layer. 
The link layer _adds its header as well with more information_, like the source- and destination IP, and MAC address. 

**ATTCK**:
`ARP poisoning` or spoofing, done by little packets that made into one. For this, logs won't be enough, it'll require deeper investigation (Wireshark for example)

Example for ARP poisoning attack:

```json
No.   Time       Source           Destination      Protocol Length Info
1     0.000000   192.168.1.1      Broadcast        ARP      60     Who has 192.168.1.10? Tell 192.168.1.1
2     0.000025   192.168.1.10     192.168.1.1      ARP      60     192.168.1.10 is at 00:11:22:33:44:55
3     1.002010   192.168.1.200    192.168.1.1      ARP      60     192.168.1.10 is at aa:bb:cc:dd:ee:ff  <-- Attacker spoof
4     1.002015   192.168.1.200    192.168.1.10     ARP      60     192.168.1.1 is at aa:bb:cc:dd:ee:ff  <-- Attacker spoof
5     1.100000   192.168.1.10     172.217.22.14    TCP      74     54433 → 80 [SYN] Seq=0 Win=64240 Len=0
```

# Network Traffic Sources and Flows

Two network traffic sources exist: endpoint and intermediary devices. These devices can be found within the LAN and WAN.


## 1. Sources

Sources are basically where the data comes from. These can be:

- **Intermediary Sources**:
	_Devices that don't originate data themselves. Just forward or process the traffic for others._ For instance:
	- Firewalls
	- Routers and switches
	- NAT gateways, proxies
	- IDS/IPS systems
	
	This traffic comes from different protocols, like
		- routing protocols (EIGRP, OSPF, BGP)
		- management protocols (SNMP, PING)
		- logging protocols (SYSLOG)
		- other supporting protocols (ARP, STP, DHCP)


- **Endpoint Sources**:
	_The devices (endpoints) that are consuming the data_. For instance:
	- employee laptops
	- servers/databases
	- IoT devices
	- mobile devices/clouds


## 2. Flows


![[66c44fd9733427ea1181ad58-1760459431334.svg]]

A network traffic flow is typically determined by the services available on the network, like SSH, SMTP or HTTPS. It also has 2 categories:

- **North-South Traffic**:
	NS traffic often flows from the LAN to the WAN and vice versa. the most well-known client-server protocols are HTTPS, DNS, SSH, VPN and many more. 
	Each of these has inbound and outbound traffic. This passes the firewall.

- **East-West Traffic**:
	EW traffic stays within the corporate LAN, so it's often less monitored. However it's still important, because of lateral movements, privilege escalations etc.
	It has many services:
	- Directory, Authentication and Identity services
	- File shares & Print services
	- Router, switching etc
	- Application communication
	- Backup & Replication
	- Monitor & Management


# Practical Examples for HOW

To collect different logs from different sources, every system has it's own methodology. 
For windows, you have `Event Logs`, while linux has Syslog

Let's say you find an interesting packet, and want to investigate. You have to:

- Install a physical **network tap**:
	_Testing Access Point_ is a physical device you place inline a network, so it can forward the logs to your IDS
	![[Pasted image 20251128182025.png]]

- Do **Port Mirroring**:
	A software approach to copy packets from one port to another. For example, Cisco has `SPAN` for it

```json
Switch(config)# monitor session 1 source interface fastEthernet0/1
Switch(config)# monitor session 1 destination interface fastEthernet0/2
```

![[Pasted image 20251128182325.png]]


## Best Practices

- **Placement**:
	Regarding to the traffic, we need to place the TAP or configure the mirror in the right place

- **Duration**:
	Regarding to the amount of traffic, you need storage and management to store it. 1Gbps line for a whole day would require 10.8TB!

- **Mirrors vs TAP**:
	taps offer close to zero performance reduction, while mirroring impacts performance in case of a huge amount of traffic went through it.
